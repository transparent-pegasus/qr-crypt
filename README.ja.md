# QR Crypt

English version: [README.md](README.md)

## 概要

> かつてオンラインに接続したことのあるデバイスは、すでに侵害されている可能性がある。
> したがって、鍵交換・暗号化・復号は、完全にオフラインを維持するデバイス上で行わなければならない。

一度オフラインデバイスとしてセットアップしたデバイスは、二度とオンラインに戻しません。廃棄する際は、記憶媒体を消去または破壊してください。アプリ自体のワイプだけでは不十分である理由は、以下の免責事項を参照してください。

QR Cryptは、恒久的にオフラインにするデバイスにインストールするProgressive Web Appです。メッセージを入力すると、アプリはそのデバイス上で暗号化を行い、暗号文をQRコードとして画面に表示します。日常的に使用するオンラインのスマートフォンでそのコードを読み取り、テキスト文字列に変換して、任意のメッセンジャーで送信します。受信者は同じ手順を逆に行います。実際のメッセージを見ることができるのは2台のオフラインデバイスだけです。ただし、メッセンジャーを監視している第三者には、メッセージのサイズや分割数は依然として見えます。

**できること**: オフラインデバイス上での暗号化と復号（AES-256-GCM、またはポスト量子暗号のML-KEM / ML-DSAスイート）、鍵の生成と管理、QRコードの表示と読み取り、PWAとしてのオフライン起動。

**できないこと**: 平文や秘密鍵をデバイス外に送信すること、鍵をクラウドに保存すること、独自の暗号アルゴリズムを使用すること、実行時にCDNに依存すること、オフライン表示を安全性の証明として扱うこと、メッセージの暗号文をアプリ内に保持すること。ユーザー自身がエクスポートしたファイル（PNGやフレームのZIP）およびクリップボードにコピーしたものは、アプリの管理外であり、ワイプの対象外です。

### 他の暗号化アプリとの違い

1つだけ違います：完全にオフラインで操作するということです。これは、アプリが強制する2つの習慣に分かれます。

* **鍵交換はオフラインで行われます。** 鍵と公開鍵はQRコードとして対面で交換します。間にサーバーは存在せず、クラウドへの鍵エスクローも、アカウント同期もありません。鍵はオフラインデバイスのIndexedDBにのみ保存されます。
* **データはオフラインデバイスとオンラインデバイスの間をQRコードとして移動します。** その隙間を渡るのは光だけです：一方の画面に表示されたQRコードと、もう一方のカメラです。

アルゴリズム自体は標準的なものです。主張しているのは、それらがどこで実行されるかについてです。

## 要件

* **1人あたり2台のデバイスが必要です。** 1台は恒久的にオフラインに保ちQR Cryptを実行するデバイス、もう1台はスクランブルされたテキストを運ぶためだけに使う通常のオンラインデバイスです。
* **ブラウザ。** Android ChromeとiOS Safariが主要ターゲットです。カメラによるQR読み取りにはSafari/iOS 16以降が必要です。Windows Chrome、macOS Safari、Edgeはリファレンス環境として記録されています（[docs/develop/browser-matrix.md](docs/develop/browser-matrix.md)）。Web CryptoまたはIndexedDBが使用できない場合、アプリは起動画面で停止し、すべての機能が利用できません。オンライン光学リレーにはさらにWeb Locks APIが必要です。オリジンに鍵が存在しないことの証明は、機密書き込みをオリジン全体で排他した状態で取得されるため、このロックを保持できないブラウザは、信頼される代わりにリレーの利用資格を拒否されます。
* **オリジン。** アプリは`https://`経由、またはローカルで`http://127.0.0.1`経由で提供される必要があります。`file://`パスから`index.html`を開いても動作しません。LAN上の通常のHTTPアドレスでも同様です。これらのコンテキストではカメラとService Workerが利用できません。
* **WebAssembly。** カメラによるQR読み取りにはWebAssemblyデコーダーを使用しており、JavaScriptのフォールバックはありません：
  * WebAssemblyが無効化またはブロックされている場合、リーダー準備ゲートがスキャン操作を無効にし、`getUserMedia`より前にカメラへのアクセスを拒否します。「QRリーダーがブロックされている」という終了状態のメッセージが表示され、iPhoneではSafari 16以降を案内します。何も読み取ることができません。
  * WebAssemblyがJITコンパイルなしで実行される場合（一部の強化またはロックダウン構成）、デコードは大幅に遅くなることが予想されます。実機での計測は行われていません（[docs/develop/browser-matrix.md](docs/develop/browser-matrix.md)）。
  * QR表示はローカルデコーダーの信号に従いません：表示側デバイスはピアのカメラが何を読み取れるかを知ることができません。1つのラベル付き互換性スイッチで選択できます。オフ（出荷時デフォルト）は1,000 B / 最小表示時間200 ms、オンは互換性優先設定の100 B / 最小表示時間2,000 msです。100 Bに収まらないアーティファクトは、そのアーティファクトに限り実効密度が上方にクランプされ、設定は保存されません。1,000 Bクランプの場合でも、スイッチはより長い2,000 msの表示時間を維持します。契約：[docs/spec/qr-protocol-v2.md](docs/spec/qr-protocol-v2.md) §6。
  * 残る唯一の入力手段は、ペイロードテキストの手動入力または貼り付けです。この入力欄は完全なペイロード文字列を受け付けますが、個々のQRフレームは受け付けません。ポスト量子暗号のメッセージは多数のフレームに分割され、ポスト量子暗号の公開鍵やアイデンティティも常にフレームとして伝送されるため、カメラが動作しない場合、ポスト量子暗号のメッセージや鍵交換は実用的ではありません。AES-256の鍵とメッセージは単一のペイロード文字列のまま使用できます。

## 使い方

### インストール方法A：署名付きZIP

これがデフォルトの方法です。オフラインデバイスがライブのアプリオリジンに一切接続しないようにします。署名付きZIPの独立検証（別チャネルからのCosignポリシー値、チェックサム確認、独立したリビルドと比較）は、インストール前に必須です。完全な手順は[docs/locales/ja/develop/install-route-a/README.md](docs/locales/ja/develop/install-route-a/README.md)にあります。アーカイブ内の`INSTALL.txt`は、オフラインデバイスに届く自己完結型のコピーです。

[docs/locales/ja/develop/install-route-a/README.md](docs/locales/ja/develop/install-route-a/README.md) §8。

### インストール方法B：ダイレクトオリジンPWA

1. オフラインに保つデバイスで、ブラウザからアプリのURLを開きます。
2. ブラウザの**インストール** / **ホーム画面に追加**アクションでインストールします。
3. インストール画面で**オフライン利用準備：準備完了**と表示されるまで待ちます。
4. そのデバイスをすべてのネットワークから切断し、そのままにしておきます。
5. デバイスがオフラインになると表示される通常の画面からアプリを使用します。

方法Bでは、受信者が実施できる完全性チェックがありません。高い保証が必要な用途では方法Aのみを使用してください。方法Aの`127.0.0.1`オリジンがライブビーコン残差を避ける理由を含む詳細：[docs/locales/ja/develop/install-route-a/README.md](docs/locales/ja/develop/install-route-a/README.md)。

### オンラインデバイスを経由したメッセージペイロード送信

2台のオフラインデバイスは同じ部屋にいる必要はありません。3台目のオンラインデバイスが、メッセージペイロードQRをテキストとして任意のメッセンジャー経由で運びます。暗号文は想定する運用であり、リレーが認証できる性質ではありません。QR Cryptの鍵を保持したことのないオンラインデバイスを使用してください。

AES-256-GCM（`sym-message` / `OCA2`）では、オフラインデバイスは常にちょうど1個のOCF2フレームを出します（単一QR硬制約）。ポスト量子暗号経路は引き続き複数フレームのOCF2転送です。リレーが受け入れるのは、検証済みのOCF2フレームで `pq-message` または `sym-message` を宣言するものだけです。

1. **送信者のオフラインデバイス** — 通常通り暗号化し、AESでは単一のOCF2フレームを、ポスト量子暗号メッセージではOCF2フレーム列を表示します。
2. **送信者のオンラインデバイス** — **リレー**ページを開き、**スキャン → テキスト**で転送のすべてのOCF2フレームを収集し、得られたテキストをコピーします。このクリップボードのコピーはアプリ外で永続化・同期される可能性があり、ワイプの対象外です。
3. **受信者のオンラインデバイス** — **リレー**ページを開き、テキストを**テキスト → QR**に貼り付け、受信者のカメラ向けにOCF2フレームを再生します。
4. **受信者のオフラインデバイス** — フレームを読み取ります。組み立てた成果物を認証する（AEAD、ポスト量子ではさらにML-DSA）のはこのデバイスだけです。

公開鍵とアイデンティティは引き続き対面で交換します。リレーが受け入れるのは正規のOCF2 `pq-message` または `sym-message` フレームのみであり、再生前に組み立てた成果物を検証しますが、受け入れた不透明なバイト列自体は認証しません。許可リストと残差の詳細：[docs/security/threat-model.md](docs/security/threat-model.md) T19 / T21。

## 暗号化

| モード | 用途 |
| --- | --- |
| **共有鍵モード**（デフォルト；AES-256-GCM、メッセージごとにHKDF） | 1対1のやり取り。対面で共有した秘密を使用します。データ量が小さく、少ないQRコードで送受信できます。共有鍵はローテートでき、置き換えられた世代でも復号できます。 |
| **公開鍵モード**（ML-KEM-1024 + ML-DSA-87 + AES-256-GCM） | 複数の送信者から1人の受信者へ送る場合や、送信者に復号用の共有秘密を持たせたくない場合。ML-KEMが受信者の公開鍵からメッセージ用の秘密を確立し、ML-DSAが送信者を確認します。本文の暗号化はどちらのモードもAES-256-GCMです。署名と公開鍵データのためメッセージは大きくなり、一連のQRコードになります。 |

ポスト量子暗号のアイデンティティと共有鍵では、ローテーションの頻度が前方秘匿性の粒度となります。ローテーションでは、復号のために置き換えられた世代を保持するため、古い世代宛てのすべてのエンベロープは、その世代を明示的に破棄するまで復号可能です。

このセッションで既に受信した同一の認証済みエンベロープは、内容が表示される前にフラグが立てられます。ポスト量子暗号メッセージでは、同じ認証済みメッセージ識別子で異なる暗号文が届いた場合も拒否されます。共有鍵モードのメッセージにはメッセージ識別子がないため、正規形エンベロープ全体のハッシュがリプレイ識別子です。このチェックはセッションスコープであり、アプリを再読み込みするとリセットされます。

ポスト量子暗号スイートは単一で、**実験的**かつ**独立した監査を受けていません**。QR CryptはFIPS 203 / FIPS 204アルゴリズムの実装を採用していますが、FIPS 140の認証や独立したセキュリティ評価を意味するものではありません。現在の状況とブロッカーについては[docs/security/security-review.md](docs/security/security-review.md)を参照してください。

## セキュリティに関する前提と免責事項

このアプリが提供する唯一の保証は、アプリケーションが意図的に平文や秘密鍵をデバイス外に送信しないということです。

以下は防御の範囲外であり、アプリ内の「セキュリティについて」画面にも記載されています：

* OS、ブラウザ、またはファームウェアの侵害
* キーロガー、画面録画、スクリーンショット
* カメラフレームをキャプチャするマルウェア
* 初回PWA取得時または再インストール時のサプライチェーン侵害
* デバイスの物理的な盗難
* ユーザー自身による秘密QRの誤共有
* ブラウザデータ削除による鍵の喪失

**オフライン表示は安全性の証明ではありません。** 現在のネットワーク状態を報告するだけです。

**オンラインにするのはインストールとリレーページのためだけです。それ以外は不可です。** オンライン中は、暗号化、復号、鍵管理、設定がブロックされます。使用中にアプリがオンラインになった場合、平文と復号結果は即座にクリアされます。

**オンライン時ワイプ**（デフォルトON）は、ネットワーク接続が確認された場合にのみ発火し、ローカルデータのベストエフォートな*論理*削除を試みます。物理的な消去は保証されません（LevelDBは追記専用、SSDはウェアレベリングを使用）。フラッシュメディアでは、デバイスの完全フォーマットでも消去は保証されません。保証が必要な場合は、メディアに適した消去手順（例：NIST SP 800-88）を実施するか、記憶媒体を物理的に破壊してください。詳細：[docs/spec/boot-and-reset-v2.md](docs/spec/boot-and-reset-v2.md)。

**更新メカニズムはありません。** 新しいバージョンを使用するには、デバイスを消去してから新規インストールしてください。鍵、アイデンティティ、または平文を含む状態を保持している、またはかつて保持していたデバイスを、消去せずにオンラインに戻さないでください。
