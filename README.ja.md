# QR Crypt

English version: [README.md](README.md)

> かつてオンラインに接続したことのあるデバイスは、すでに侵害されている可能性がある。
> したがって、鍵交換・暗号化・復号は、完全にオフラインを維持するデバイス上で行わなければならない。

QR Cryptは、恒久的にオフラインに保つデバイスで使うProgressive Web Appである。メッセージを入力すると、アプリはそのデバイス上で暗号化し、暗号文をQRコードとして表示する。日常使いのオンラインのスマートフォンがそのコードを読み取り、テキストとして任意のメッセンジャーで送る。受信者は逆の手順をたどり、自分のオフラインデバイスで復号する。

## 仕組み

- **処理はオフラインデバイスが行う。** 鍵の生成と管理、暗号化、復号を行い、実行時にCDNへ依存しない。一度セットアップしたら二度とオンラインに戻さない。廃棄時は記憶媒体を消去または破壊する。アプリ自身のワイプだけでは不十分である（[セキュリティ](#セキュリティ)参照）。
- **鍵は対面で渡す。** 鍵と公開鍵はQRコードとして対面で交換する。サーバー、クラウドへの鍵エスクロー、アカウント同期はない。アプリが管理する永続ストレージ内では、鍵レコードはオフラインデバイスのIndexedDBにのみ置かれる。共有AES鍵は、エクスポート可能な`OCK2`秘密鍵QRとして渡す。
- **フィンガープリントで相手を確かめる。** インポートしたアイデンティティや保存済みのアイデンティティを確認する前に、独立したチャネルで意図した相手と**アイデンティティのフィンガープリントの16進数64桁すべて**を比較する。共有鍵のインポートでも、鍵のフィンガープリント64桁すべてを同じく比較する。確認操作は、比較したこともチャネルの信頼性も証明しない（[脅威モデル](docs/security/threat-model.md) T6）。
- **隙間を渡るのは光だけ。** QR転送経路では、一方の画面のQRコードと他方のカメラによって、オフラインデバイスとオンラインデバイスの間をデータが移動する。アプリはメッセージの暗号文を保持しない。エクスポートしたファイル（PNG、またはフレームのZIP）をリムーバブルメディアで運ぶ経路と、クリップボードでテキストを運ぶ経路は別の選択肢であり、この主張の範囲外で、アプリの管理とワイプの対象外である。
- **観測者にはメタデータが見える。** 転送を監視する第三者には、メッセージの種類、固定の共有鍵識別子または受信者鍵識別子、サイズ、フレーム数が見える。共有鍵メッセージでは、送信者が申告した作成時刻も見える。同じ鍵識別子の繰り返しから、転送同士を関連付けられる。
- **標準アルゴリズムのみ。** AES-256-GCM、またはポスト量子暗号のML-KEM-1024 / ML-DSA-87スイート。主張しているのは、それらをどこで実行するかである。

## 導入

### 方法A：署名付きZIP（デフォルト）

方法Aは、オフラインデバイスがライブのアプリオリジンに一切接続しないようにする。インストール前に、署名付きZIPを独立に検証する：別チャネルから得たCosignポリシー値、チェックサム、独立したリビルドと比較。[完全な手順](docs/locales/ja/develop/install-route-a/README.md)に従う。アーカイブ内の`INSTALL.txt`は、オフラインデバイスに届く、その手順の自己完結型のコピーである。

### 方法B：ダイレクトオリジンPWA

1. オフラインに保つデバイスで、ブラウザからアプリのURLを開く。
2. ブラウザの**インストール** / **ホーム画面に追加**アクションでインストールする。
3. インストール画面に**オフライン利用準備：準備完了**と表示されるまで待つ。
4. デバイスをすべてのネットワークから切断し、そのまま保つ。
5. デバイスがオフラインになると表示される通常の画面から、アプリを使う。

方法Bには、利用者が実施できる完全性チェックがない（リスクは[方法Aの手順](docs/locales/ja/develop/install-route-a/README.md)の§1で説明している）。方法Bのデバイスはライブのオリジンも保持し続けるため、再接続すると、ワイプが発火する前に到達性プローブがそのオリジンに届く。方法Aのインストールサーバーを停止し、予約済みポートを再利用しなければ、`127.0.0.1`オリジンに応答する相手はいない。高い保証が必要な用途では方法Aのみを使用する。

## リレー

2台のオフラインデバイスは同じ部屋にある必要はない。3台目のオンラインデバイスが、メッセージのテキストを任意のメッセンジャーで運ぶ。QR Cryptの鍵を保持したことのないオンラインデバイスを使う。暗号文だけを運ぶことは想定する運用であり、リレーが検証できる性質ではない。

1. **送信者のオフラインデバイス：** 暗号化する。AESでは1個のOCF2フレーム、ポスト量子暗号メッセージではフレーム列を表示する。
2. **送信者のオンラインデバイス：** **リレー**ページの**QR → テキスト**ですべてのフレームを集め、テキストをメッセンジャーにコピーする。
3. **受信者のオンラインデバイス：** **リレー**ページで**テキスト → QR**にテキストを貼り付け、フレームを再生する。
4. **受信者のオフラインデバイス：** フレームを読み取る。組み立てたメッセージを認証する（AEAD、ポスト量子暗号ではさらにML-DSA）のは、このデバイスだけである。

単一フレームのメッセージでは、送信者のオンラインデバイスの**QR → QR**が手順2と3を置き換える。フレームをQR画像として描き直すので、画像を貼れるメッセンジャーに送れば、受信者はチャット画面から直接読み取れる。フレームの検証は**QR → テキスト**と同一で、復号も認証も行わない。複数フレーム（ポスト量子暗号）の転送は拒否する。

コピーしたテキストと画像は、アプリ外で永続化・同期される可能性があり、ワイプの対象外である。リレーが受け入れるのは検証済みのOCF2 `pq-message` / `sym-message` フレームだけで、鍵は受け入れない。許可リストと残差：[脅威モデル](docs/security/threat-model.md) T19 / T21。

## 要件

- **1人あたり2台のデバイス：** 恒久的にオフラインに保つ1台と、リレー用のオンラインの1台。
- **ブラウザ：** 主要ターゲットはAndroid ChromeとiOS Safari。カメラでのQR読み取りにはSafari/iOS 16以降が必要。Windows Chrome、macOS Safari、Edgeはリファレンス環境である（[ブラウザマトリクス](docs/develop/browser-matrix.md)）。Web CryptoまたはIndexedDBがないと、アプリは起動画面で停止する。リレーにはさらにWeb Locks APIが必要で、これがないブラウザはリレーを使えない。
- **オリジン：** `https://`、またはローカルの`http://127.0.0.1`。`file://`パスやLAN上の通常のHTTPでは、カメラとService Workerが使えないため動作しない。
- **WebAssembly：** カメラでのQR読み取りはWebAssemblyデコーダーを使い、JavaScriptのフォールバックはない。WebAssemblyがブロックされていると、アプリはカメラへのアクセス前に読み取りを無効化し、QRリーダーがブロックされている旨を表示する。iPhoneではSafari 16以降を案内する。JITなしで動く場合（一部の強化・ロックダウン構成）、デコードは大幅に遅くなる見込みで、その程度は実機で計測していない。
- **カメラで読み取れない場合：** 入力できるのは完全なペイロード文字列の手入力か貼り付けだけで、個々のフレームは受け付けない。ポスト量子暗号のメッセージ、公開鍵、アイデンティティは常にフレームで運ぶため、カメラなしでは実用的でない。AESの鍵とメッセージは、単一の文字列のまま使える。
- **表示：** 送信側は相手のカメラが何を読めるかを知り得ないため、QR表示はローカルのデコーダーに従わない。ラベル付きの互換性スイッチで、小さいフレームを長く表示できる。値とアーティファクトごとのクランプ：[QRプロトコル](docs/spec/qr-protocol-v2.md) §6。

## 暗号化

| モード | 用途 |
| --- | --- |
| **共有鍵モード**（デフォルト；AES-256-GCM、メッセージごとにHKDF） | 対面で共有した秘密を使う1対1のやり取り。各メッセージは必ず1個のQRコードになる。鍵はローテートでき、置き換えた世代でも復号できる。 |
| **公開鍵モード**（ML-KEM-1024 + ML-DSA-87 + AES-256-GCM） | 複数の送信者から1人の受信者へ送る場合や、復号できる秘密を送信者に持たせたくない場合。ML-KEMが受信者の公開鍵からメッセージ用の秘密を確立し、ML-DSAが送信者を確認する。署名と鍵データのため、各メッセージは一連のQRコードになる。 |

ポスト量子暗号のアイデンティティと共有鍵では、ローテーションの頻度が前方秘匿性の粒度になる。置き換えた世代は復号のために残るため、その世代宛てのエンベロープは、世代を明示的に破棄するまで復号できる。

このセッションで既に受信した同一の認証済みエンベロープには、内容を表示する前にフラグが立つ。同じポスト量子暗号メッセージ識別子が異なる暗号文で届くと拒否する。このチェックはセッション単位で、再読み込みでリセットされる（[脅威モデル](docs/security/threat-model.md) §5）。

ポスト量子暗号スイートは単一で、**実験的**かつ**独立した監査を受けていない**。FIPS 203 / FIPS 204のアルゴリズムを実装しているが、FIPS 140の認証や独立したセキュリティ評価を意味しない。現状とブロッカー：[セキュリティレビュー](docs/security/security-review.md)。

## セキュリティ

唯一の保証は、アプリが意図的に平文や秘密鍵をデバイス外に送信しないことである。

以下は防御の範囲外であり、アプリ内の**セキュリティについて**画面にも記載している：

- OS、ブラウザ、またはファームウェアの侵害
- キーロガー、画面録画、スクリーンショット
- カメラフレームをキャプチャするマルウェア
- 初回PWA取得時または再インストール時のサプライチェーン侵害
- デバイスの物理的な盗難
- ユーザー自身による秘密QRの誤共有
- ブラウザデータ削除による鍵の喪失

**オフライン表示は安全性の証明ではない。** 現在のネットワーク状態を報告するだけである。

**オンラインにするのは、インストールとリレーページのためだけである。** オンライン中は、暗号化、復号、鍵管理、設定がブロックされる。使用中にアプリがオンラインになると、平文と復号結果を即座にクリアする。

**オンライン時ワイプ**（デフォルトON）は、ネットワーク接続が確認された場合にのみ発火し、ローカルデータのベストエフォートな*論理*削除を試みる。物理的な消去は保証されない（LevelDBは追記専用、SSDはウェアレベリングを使用）。フラッシュメディアでは、デバイスの完全フォーマットでも消去は保証されない。保証が必要な場合は、メディアに適した消去手順（例：NIST SP 800-88）を実施するか、記憶媒体を破壊する。詳細：[起動とリセット](docs/spec/boot-and-reset-v2.md)。

**アプリ内アップグレードはない。** インストール元のオリジンに到達できると、ブラウザのService Workerライフサイクルが置換コードを取得・有効化し得る。恒久的なオフライン運用は配備上の要件であり、ブラウザの保証ではない（[脅威モデル](docs/security/threat-model.md) §5）。新しいバージョンを使うには、デバイスを消去してから新規インストールする。鍵、アイデンティティ、平文を含む状態を保持している、または保持していたデバイスは、消去せずにオンラインに戻さない。
