# QR Crypt Threat Model

## 1. Protected assets

| Asset                                              | Storage location                                                          | Sensitivity                                                    |
| -------------------------------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Plaintext / decrypted message body                 | React memory only (persistence forbidden)                                 | Highest                                                        |
| AES symmetric key                                  | IndexedDB (CryptoKey, extractable — required by the QR exchange spec)     | Highest                                                        |
| RSA private key                                    | IndexedDB (CryptoKey, **non-extractable**)                                | Highest                                                        |
| Symmetric-key QR / private-key backup QR (future)  | No in-app persistence (on-screen display + explicit user export only)     | Highest                                                        |
| Ciphertext QR / relay frame strings                | No frame-derived value in app-managed IndexedDB, localStorage, or CacheStorage. Session memory may hold canonical `OCF2:` strings, untrusted outer-header metadata, and rendered QR data URLs; explicit clipboard copy may persist or sync outside the app and outside any wipe; clearing a session releases app references best-effort only | Confidential if the inner artifact is ciphertext (cannot be decrypted without the key); outer header fields are attacker-controlled metadata |
| Public-key QR                                      | Same as above                                                             | Public                                                         |
| Settings (scheme, EC level, etc.)                  | IndexedDB / theme `oc-theme` in localStorage                              | Low                                                            |
| Offline acknowledgement pending state              | localStorage `oc-offline-ack-pending="1"`                                 | Low (non-sensitive; contains no keys, plaintext, or ciphertext) |

## 2. Scope of guarantees

What this app guarantees extends only to: **the application does not intentionally transmit plaintext, private keys, or symmetric keys off the device**. Implementation-level supports:

- Zero external API communication as an app feature (no third-party or cross-origin clients). Permitted network traffic is fetching the PWA itself and its static assets (including service-worker static revalidation), the same-origin `GET /reachability-sentinel.txt` probe that gates wipe-on-online (see T18), and the recurring same-origin display probe `HEAD /manifest.webmanifest?reach=…` (every 4 s while reachable, every 15 s otherwise). None of these requests is user-data-bearing or frame-data-bearing
- CSP `connect-src 'self'` and related headers (`public/_headers`) also block runtime external transmission at the browser level
- No analytics, logging, or error-reporting SDKs; no external fonts or CDNs
- Production builds never write plaintext, keys, or QR contents to the console
- Plaintext persistence is forbidden (in both localStorage and IndexedDB). An auto-clear timer runs when the app is left in the background

## 3. Out of scope (explicit non-goals — full text shown in the in-app "About security" settings section)

1. Compromise of the OS, browser, or firmware
2. Keyloggers, screen recording, screenshots
3. Malware that captures camera frames
4. Supply-chain compromise at initial PWA installation or reinstallation
5. Physical theft of the device
6. The user themselves accidentally sharing a secret QR
7. Loss of keys through browser data deletion

The "offline" indicator is auxiliary information about network state; it is never treated or presented as proof of safety.
The explanatory screen and acknowledgement checkbox shown when the device returns to offline do not verify or restore the safety of the device.

## 4. Attacker model and countermeasures

As a cross-cutting countermeasure for T8/T11, OnlineGate fail-closes encryption, decryption, key management, storage, and settings while online. On a logically clean origin whose sensitive-store scan completed without error, the online gate may forward exact canonical OCF2 strings whose **untrusted outer header declares** `pq-message`. The relay does not assemble or verify the artifact, total hash, inner type, AEAD, or signature. It writes no frame-derived value to app-managed storage or CacheStorage and makes no frame-bearing network request. Explicit clipboard copy/paste may persist or sync outside the app and outside any wipe; the camera sees ambient pixels; displayed QR images can be captured by the browser or OS. The offline endpoint performs authoritative completion and cryptographic validation. Clean-origin eligibility is a current logical-absence check under a completed scan — it does not prove historical non-use or physical erasure, and a second tab writing a key during a relay session is a disclosed residual race. Devices that still hold keys, PQ identity rows, or a Vault key take the block-and-wipe path, so the feature never creates an incentive to bring a key-holding device online. The offline→online transition fires TransientClear, which immediately clears plaintext, decryption results, and result payloads. A displayed-online recommit restarts boot's sentinel probe at most once, but the displayed edge itself is never grounds for, nor a direct trigger of, a wipe. While the display probe is in a false-negative state, there is residual risk that InstallScreen does not block. The offline indicator itself is never treated as proof of safety.

## 5. Design trade-offs (explicit)

- **The symmetric key is extractable**: generating the symmetric-key QR is a spec requirement. The exposure surface is reduced by T3's UI countermeasures. For counterparts needing stronger protection, the RSA scheme is recommended (its private key is non-extractable).
- **No signatures or sender authentication (v1)**: authenticity of a ciphertext (who created it) is not guaranteed. Introducing signatures into the envelope would be a v2 change.
- **createdAt is metadata**: there is no replay-protection mechanism (for offline use this is left to the recipient's contextual judgment). AAD sealing only makes tampering detectable.
- **Private-key backup (OCB1) not implemented**: flag permanently OFF. Any implementation must satisfy these conditions: encryption under a passphrase-derived key, a random salt/IV, and a restore test.
- **No update path**: eliminating the update path is a maintainer decision on operational policy. Devices that hold or have held protected material (keys, PQ identities, Vault key, or plaintext-bearing session state) operate permanently offline; a new version is installed fresh only after the device has been sanitized. A dedicated clean-origin relay device is not a key/plaintext-bearing device and may stay online for the optical relay only. A simple full format alone does not guarantee erasure on flash/SSD media — use a media-appropriate sanitization procedure (e.g. NIST SP 800-88) or destroy the media when assurance matters.

## 6. Mapping to verification

- Zero external transmission: e2e tests confirm that every in-page network request has origin self only, plus CSP headers
- Plaintext non-persistence / cleanliness of the localStorage allowlist `{oc-theme, oc-lang, oc-offline-ack-pending}` and the pending value `"1"`: integration and e2e tests
- Decryption failure on AAD mismatch, tampering, and wrong keys: unit tests
- IV uniqueness and length: unit tests
- Strong-confirmation and warning UI: UI tests

- **Destructiveness of RSA removal**: after updating to v2, existing OCM1-RSA ciphertexts are unrecoverable (the non-extractable RSA private key cannot be rescued). The update UI and the README state this explicitly, together with the legacy-item count and a deletion path (no decrypt-only compatibility is retained).
- Still maintained in v2: plaintext non-persistence; **no user-data-bearing or frame-data-bearing network request** (same-origin static fetch, sentinel GET, and recurring manifest HEAD remain permitted — not "zero network"); and a localStorage allowlist of `{oc-theme, oc-lang, oc-offline-ack-pending}` only. `oc-lang` holds only the UI language (`en`/`ja`); the acknowledgement marker is a non-sensitive pending state with the fixed value `"1"`. The online relay exception (T19) does not weaken these rules for key/plaintext-bearing devices.
