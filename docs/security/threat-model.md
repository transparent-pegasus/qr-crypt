## 2. Scope of guarantees

What this app guarantees extends only to: **the application does not intentionally transmit plaintext, private keys, or symmetric keys off the device**. This guarantee assumes that the installed code is authentic. Implementation-level supports:

- Zero external API communication as an app feature (no third-party or cross-origin clients). Permitted network traffic is fetching the PWA itself and its static assets (including service-worker static revalidation), the same-origin `GET /reachability-sentinel.txt` probe that gates wipe-on-online (see T18), and the recurring same-origin display probe `HEAD /manifest.webmanifest?reach=…` (every 4 s while reachable, every 15 s otherwise). None of these requests is user-data-bearing or relay-payload-bearing
- CSP `connect-src 'self'` and related directives are delivered as response
  headers from `public/_headers`; production builds also inject the supported
  directives as a meta CSP fallback. `frame-ancestors` remains response-header
  only because browsers ignore it in a meta CSP. `script-src` is
  `'self' 'wasm-unsafe-eval'`; the WebAssembly token was added 2026-07-26 for
  the zxing-wasm camera reader and lets any script that already executes
  compile arbitrary WebAssembly at this origin. It does not enable
  `'unsafe-eval'`, JavaScript string evaluation, or cross-origin fetches
- **`_headers` is a host construct, and a Route A install is not served by that
  host.** `public/_headers` is applied by Cloudflare Pages and by this
  repository's own `scripts/serve-dist.mjs`; an arbitrary static server on the
  offline device most likely ignores it. What survives that: the meta CSP
  fallback, and `Referrer-Policy` via `<meta name="referrer">` in
  `index.html`. What does **not** survive, because no meta equivalent exists:
  `Permissions-Policy` (T12), `X-Content-Type-Options`, `X-Frame-Options`,
  `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy`, and CSP
  `frame-ancestors`. Nothing in the app detects their absence. Treat every one
  of those as a control the deployment may simply not have; the install
  procedure's server requirement is the only thing that supplies them. On a
  loopback origin that is never networked and frames nothing, the practical
  exposure is low — but the threat model must not credit a control that the
  serving environment silently dropped
- No analytics, logging, or error-reporting SDKs; no external fonts or CDNs
- Production builds never write plaintext, keys, or QR contents to the console
- Plaintext persistence is forbidden (in both localStorage and IndexedDB). An auto-clear timer runs when the app is left in the background

## 3. Out of scope (explicit non-goals — full text shown in the in-app "About security" settings section)

1. Compromise of the OS, browser, or firmware
2. Keyloggers, screen recording, screenshots
3. Malware that captures camera frames
4. Supply-chain compromise at initial PWA installation or reinstallation
5. Physical theft of the device
6. The user themselves accidentally sharing a secret QR
7. Loss of keys through browser data deletion

Out of scope is not the same as unexamined. Physical and operational environment
techniques — optical capture of a displayed QR, screen emanation, acoustic
keyboard emanation, device custody, removable media, air-gap covert channels,
operator conditions — are catalogued with their evidence and control class in
[environment-threat-catalog.md](environment-threat-catalog.md). That catalog
mints no `T` identifier and claims no countermeasure this application has; it
records what the deployment, not the code, has to answer for.

The "offline" indicator is auxiliary information about network state; it is never treated or presented as proof of safety (§4 OnlineGate note).
The explanatory screen and acknowledgement checkbox shown when the device returns to offline do not verify or restore the safety of the device.

## 4. Attacker model and countermeasures

> **Status note (v2) — what is active, what is removed.**
> **Active:** symmetric HKDF-AES (`A256GCM` UI / wire suite
> `HKDF-SHA256+A256GCM`, prefixes `OCA2` / `OCK2`, the shipped product default —
> see `.env.prod`) and the single post-quantum suite
> `ML-KEM-1024+ML-DSA-87+HKDF-SHA256+A256GCM` (every PQ message is signed).
> **Removed from every active union, write path, and crypto/wire boundary:** the v1 wire family (`OCM1` / `OCK1` /
> `OCP1` / `OCB1`, cbor-x envelopes), RSA vocabulary (`RSA-OAEP-3072`,
> `rsa-key-pair`, `KeyKind`), unsigned ML-KEM suites, `ML-KEM-768`, `ML-DSA-65`,
> the `balanced` profile, `MLKEM1024_A256GCM`, and the `requireSignature` /
> `defaultPqProfile` preferences. The sole safety exception is boot's read-only
> acceptance of a stored `defaultAlgorithm: "RSA-HYBRID"`: the repository
> normalizes it to `A256GCM`, but boot must preserve `wipeOnOnline:false` rather
> than turn an obsolete preference into a future wipe trigger. No RSA key,
> cryptographic, write, or wire path remains.

## 5. Design trade-offs (explicit)

- **The symmetric key is extractable**: generating the `OCK2` symmetric-key QR is a spec requirement. The exposure surface is reduced by T3's UI countermeasures. Stronger non-extractable protection belongs to a PQ identity, whose seeds are stored only under the non-extractable Vault key (T13). Symmetric keys support active/rotated lineage; encryption and OCK2 share use the active head only, while decrypt resolves any generation by `keyId`.
- **Symmetric messages authenticate the envelope, not the sender**: `sym-message` AAD binds `version` / `type` / `suite` / `keyId` / `createdAt`. Sender authentication for the post-quantum path is ML-DSA-87 on every PQ message (T15).
- **createdAt is metadata; window-memory receipts cover re-presentation**: one loaded app window's JavaScript realm keeps a module-local receipt map (`src/features/receipt-cache.ts`), bounded at `MAX_SESSION_RECEIPTS` with oldest-first eviction. A matching ciphertext hash is flagged before plaintext is shown; an authenticated message ID seen with a different ciphertext is refused. The map is not shared with another tab or window of the same app. Reload/restart, transient clear, or wipe resets it, and evicted entries become undetectable again. PQ receipts use recipient KEM key ID plus the authenticated `messageId` as identity and compare the ciphertext hash for the verdict. Symmetric (`sym-message`) receipts use the symmetric key ID plus ciphertext hash (no inner `messageId`). Neither case authenticates a sender by itself. `createdAt` remains sender-asserted and is never a freshness source. Nothing frame- or assembled-artifact-derived is persisted, so the asset table at §1, T11, T19, and the clean-origin boot gate are unchanged by this work.
- **Private-key backup (`OCB2`) not implemented**: the `OCB2` prefix is reserved and unconditionally rejected — there is no feature flag. Any implementation must satisfy these conditions: encryption under a passphrase-derived key, a random salt/IV, and a restore test.
- **No update path**: eliminating the update path is a maintainer decision on operational policy. Devices that hold or have held protected material (keys, PQ identities, Vault key, or plaintext-bearing session state) operate permanently offline; a new version is installed fresh only after the device has been sanitized. A dedicated clean-origin relay device is not a key/plaintext-bearing device and may stay online for the optical relay only. A simple full format alone does not guarantee erasure on flash/SSD media — use a media-appropriate sanitization procedure (e.g. NIST SP 800-88) or destroy the media when assurance matters.

- Decryption failure on AAD mismatch, tampering, and wrong keys: unit tests
- IV uniqueness and length: unit tests
- Strong-confirmation and warning UI: UI tests
- Session receipt cache (first-seen / already-received / message-id-reused, bound, wipe clear): `tests/unit/receipt-cache.test.ts`
- Decrypt-page replay gate, `MESSAGE_ID_REUSED` refusal, and identity-unconfirmed alert: `tests/ui/decrypt-page.test.tsx`
- `hkdfSalt` absent from every active schema, encoder, decoder, and type; an old-format envelope carrying it rejected rather than migrated; the 131-byte overhead and 853-byte symmetric ceiling; identical plaintext still producing distinct ciphertext; a one-bit `iv` mutation still failing to open (T9 / T21): `tests/pq/hkdf-salt-wire-removal.test.ts`, `tests/pq/hkdf-salt-derivation.test.ts`
- Unicode format characters in decrypted plaintext counted by code point, ordinary English / Japanese / CJK / emoji / combining marks not flagged, and the rendered plaintext left byte-identical while the alert is shown (T21): `tests/unit/suspicious-format-characters.test.ts`, `tests/ui/decrypt-page.test.tsx`
- The six non-CSP security headers actually served, and the `<meta name="referrer">` fallback present in the built page (§2): `tests/e2e/security.spec.ts`
