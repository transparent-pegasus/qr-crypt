## 2. Scope of guarantees

What this app guarantees extends only to: **the application does not intentionally transmit plaintext, private keys, or symmetric keys off the device**. This guarantee assumes that the installed code is authentic. Implementation-level supports:

- Zero external API communication as an app feature (no third-party or cross-origin clients). Permitted network traffic is fetching the PWA itself and its static assets (including service-worker static revalidation), the same-origin `GET /reachability-sentinel.txt` probe that gates wipe-on-online (see T18), and the recurring same-origin display probe `HEAD /manifest.webmanifest?reach=…` (every 4 s while reachable, every 15 s otherwise). None of these requests is user-data-bearing or relay-payload-bearing
- CSP `connect-src 'self'` and related directives are delivered as response
  headers from `public/_headers`; production builds also inject the supported
  directives as a meta CSP fallback. `frame-ancestors` remains response-header
  only because browsers ignore it in a meta CSP. `script-src` is
  `'self' 'wasm-unsafe-eval'`; the WebAssembly token was added 2026-07-26 for
  the zxing-wasm camera reader and lets any script that already executes
  compile arbitrary WebAssembly at this origin. It does not enable
  `'unsafe-eval'`, JavaScript string evaluation, or cross-origin fetches
- No analytics, logging, or error-reporting SDKs; no external fonts or CDNs
- Production builds never write plaintext, keys, or QR contents to the console
- Plaintext persistence is forbidden (in both localStorage and IndexedDB). An auto-clear timer runs when the app is left in the background

## 3. Out of scope (explicit non-goals — full text shown in the in-app "About security" settings section)

1. Compromise of the OS, browser, or firmware
2. Keyloggers, screen recording, screenshots
3. Malware that captures camera frames
4. Supply-chain compromise at initial PWA installation or reinstallation
5. Physical theft of the device
6. The user themselves accidentally sharing a secret QR
7. Loss of keys through browser data deletion

The "offline" indicator is auxiliary information about network state; it is never treated or presented as proof of safety (§4 OnlineGate note).
The explanatory screen and acknowledgement checkbox shown when the device returns to offline do not verify or restore the safety of the device.

## 4. Attacker model and countermeasures

> **Status note (v2) — what is active, what is removed, what is retained.**
> **Active:** the v1 AES-256-GCM path (`A256GCM`, the shipped product default,
> see `.env.prod`) and the v2 post-quantum paths — ML-KEM-1024 envelopes with
> optional ML-DSA-87 signatures. **Removed:** RSA key creation and RSA
> decryption; no RSA operation can be performed, and schema validation rejects
> non-`A256GCM` OCM1 messages (§7). **Retained as acceptance-only vocabulary:**
> the `OCP1` / `RSA-OAEP-3072` public-key envelope still passes schema
> validation and stored `rsa-key-pair` / `public-key` records still load, so the
> v1 wire vocabulary stays readable without being operable. Rows and trade-offs
> below that discuss the RSA design (T4's non-extractable-key rationale, the §5
> symmetric-key trade-off) describe the retired v1 design and are historical.
> "No signatures (v1)" does not apply to v2 signed envelopes.

While the display probe is in a false-negative state, there is residual risk that InstallScreen does not block. The offline indicator itself is never treated as proof of safety.

## 5. Design trade-offs (explicit)

- **The symmetric key is extractable**: generating the symmetric-key QR is a spec requirement. The exposure surface is reduced by T3's UI countermeasures. The retired v1 design named the RSA scheme as the stronger-protection alternative (non-extractable private key); in the current implementation that role belongs to a PQ identity, whose seeds are stored only under the non-extractable Vault key (T13).
- **No signatures or sender authentication (v1)**: authenticity of a ciphertext (who created it) is not guaranteed in v1. The shipped mechanism for sender authentication is v2's ML-DSA signed suites (T15).
- **createdAt is metadata; window-memory receipts cover re-presentation**: one loaded app window's JavaScript realm keeps a module-local receipt map (`src/features/receipt-cache.ts`), bounded at `MAX_SESSION_RECEIPTS` with oldest-first eviction. A matching ciphertext hash is flagged before plaintext is shown; an authenticated message ID seen with a different ciphertext is refused. The map is not shared with another tab or window of the same app. Reload/restart, transient clear, or wipe resets it, and evicted entries become undetectable again. Unsigned PQ uses recipient KEM key ID plus the authenticated `messageId` as receipt identity and compares the ciphertext hash for the verdict. Only v1 AES lacks a message ID and uses recipient key ID plus ciphertext hash as its identity. Neither case authenticates a sender. `createdAt` remains sender-asserted and is never a freshness source. Nothing frame- or OCM1-derived is persisted, so the asset table at §1, T11, T19, and the clean-origin boot gate are unchanged by this work.
- **Private-key backup (OCB1) not implemented**: the `OCB1` and `OCB2` prefixes are reserved and unconditionally rejected — there is no feature flag. Any implementation must satisfy these conditions: encryption under a passphrase-derived key, a random salt/IV, and a restore test.
- **No update path**: eliminating the update path is a maintainer decision on operational policy. Devices that hold or have held protected material (keys, PQ identities, Vault key, or plaintext-bearing session state) operate permanently offline; a new version is installed fresh only after the device has been sanitized. A dedicated clean-origin relay device is not a key/plaintext-bearing device and may stay online for the optical relay only. A simple full format alone does not guarantee erasure on flash/SSD media — use a media-appropriate sanitization procedure (e.g. NIST SP 800-88) or destroy the media when assurance matters.

## 6. Mapping to verification

- Zero external transmission: e2e tests confirm that every in-page network request has origin self only, plus CSP headers
- Plaintext non-persistence / cleanliness of the localStorage allowlist `{oc-theme, oc-lang, oc-offline-ack-pending, oc-online-tab}`, the pending value `"1"`, and the tab value `top`/`relay`: integration and e2e tests
- Decryption failure on AAD mismatch, tampering, and wrong keys: unit tests
- IV uniqueness and length: unit tests
- Strong-confirmation and warning UI: UI tests
- Session receipt cache (first-seen / already-received / message-id-reused, bound, wipe clear): `tests/unit/receipt-cache.test.ts`

Canonical CBOR separately caps one map at 8 entries (the largest active protocol shape), the decoded value at 13 total map entries, keys at 18 UTF-8 bytes (`senderSigningKeyId`, the longest decoded key), and text at 300 UTF-8 bytes; a byte cap alone bounds neither entry count nor retained heap. V2 decoding uses null-prototype maps and no process-lifetime cache of attacker-supplied keys, then performs the canonical re-encode equality check. The online OCM1 path accepts at most `MAX_PAYLOAD_CHARS` (8192 characters, `src/lib/limits.ts`), then runs `cbor-x` decode, recursive unsupported-value validation, strict schema parsing, and a complete canonical re-encode equality check | A v2 adversary can still force roughly 128 kilobytes of assembly plus canonical re-encode copies and roughly 171 kilobytes of pasted text. OCM1 decoding creates decoded maps and typed arrays plus a second encoded copy; release of those objects is garbage-collector-governed and therefore best-effort. Garbage-collected copies may remain locally after references are released. This is an availability and local-memory residual, not a confidentiality residual |
| T21 | Covert egress through the relay by a compromised offline device: a counterfeit offline-device app embeds keys or plaintext in ostensible ciphertext, displays it as `OCF2:` frames or one `OCM1:` message, and relies on the user and the user's online device to carry it | Effectively none. The hop cannot authenticate accepted opaque bytes; see T19 for the allowlist and structural checks a compromised sender still satisfies | Capacity is path-specific: up to 128,000 B across an OCF2 frame set versus a 2,953-character single OCM1. OCM1 adds an easier single-QR covert path even though OCF2 still dominates capacity. `frameCount` and `totalByteLength` are observable in every OCF2 outer frame, but accepted message-payload bytes are opaque, so an observer cannot tell whether a transfer is legitimate ciphertext or covert exfiltration. The claim that plaintext is not handed to a third party therefore depends entirely on installation integrity (non-goal 4); this is why the installation route A/B choice determines the overall guarantee |
| T22 | Imported-bundle key-ID shadowing: an attacker-supplied public bundle asserts a stored `signing.keyId` (or `kem.keyId`) and displaces the legitimate record because resolution once took the newest import | Unique indexes on `signing.keyId` and `kem.keyId` in `pqPublicBundles`; `saveBundle` refuses a re-import with equal KEM/signing algorithms and equal public-key bytes as `DUPLICATE_KEY`, and refuses every other key-ID collision as `KEY_ID_CONFLICT`, including partial collisions. If either indexed match is revoked, it always reports `KEY_ID_CONFLICT`, including for equal key material; signing/KEM resolution is an exact index lookup that treats revoked as unknown; decrypt UI separates signature validity from identity confirmation | Disabling hides the row and permanently reserves both its signing and KEM key IDs in that installation. It cannot be undone or deleted from the key screen afterwards; only a full local wipe clears the reservation. Deleting instead is an alternative only before disabling. The out-of-band fingerprint comparison remains the only person-binding |

- **No RSA decryption path**: no decrypt-only compatibility for OCM1-RSA is retained, and schema validation rejects non-`A256GCM` OCM1 messages. A non-extractable RSA private key cannot be rescued, so any such ciphertext is unrecoverable.
